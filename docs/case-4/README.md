# Кейс 4: буферизация и back pressure

Для `acc-18` я запустил тест с исходными параметрами: **200 запросов/с, 6000 покупок, дедлайн 3000 мс**. Аккаунт принимает 110 запросов/с, обрабатывает платёж в среднем за секунду и берёт 30 за вызов.

Я ограничил количество незавершённых оплат. Если места закончились, магазин сразу отвечает **429**, а тестер повторяет запрос позже. Отказ происходит до изменения заказа и обращения к платёжной системе, поэтому денег не стоит. Back pressure включается свойством `payment.backpressure.enabled=true`; его можно отключить.

Размер буфера рассчитывается из лимитов аккаунта и бюджета времени:

```text
μ = min(rateLimitPerSec, parallelRequests / averageProcessingTimeSeconds)
C = min(parallelRequests, ceil(μ × processingUpperBoundSeconds))
Q = floor(μ × max(0, deadlineSeconds − processingUpperBoundSeconds − 1))
B = C + Q
```

Для этого кейса получаются **220 мест и пауза повтора `ceil(1000 / μ)` = 10 мс**. До резервирования места приём дополнительно ограничен 110 оплатами/с; это не даёт заполнить пул задачами, ожидающими сетевую квоту. Верхняя граница обработки 2 с подтверждена кодом локального тестера и задаётся отдельно: одного среднего времени для её определения недостаточно. При запуске лимит постепенно растёт с одного места до 220, чтобы холодная JVM успевала прогреться на реальных запросах.

Перед сетевой отправкой скользящее окно ограничивает частоту до 110 стартов за секунду. Место в буфере освобождается после завершения всей оплаты. Для локальной проверки использовал HTTP/1.1 и очередь принятия TCP-соединений Jetty 1024: это убрало ошибки соединений при стартовом всплеске.

## Оптимизация после защиты, 5 ноября

Секундный `Retry-After` замедлял весь генератор. Пауза из пропускной способности сократила прогон до 96,6 с. Дополнительное входное окно 110 оплат/с позволило увеличить запас мест до 220 и получить **72,7 с** без просроченных оплат. В самом тестере есть ожидание границы секунды, поэтому полностью ровного потока он не создаёт.

Убрал отдельный диспетчер с опросом каждые 1 мс, промежуточную очередь и семафор: ограниченный `ThreadPoolExecutor` сам обслуживает очередь и ограничивает параллельность. Также удалил неиспользуемый вариант `tickBlocking()` без дедлайна. Прогрев, feature flag, внешний rate limit и дедлайн сохранены.

Все варианты проверял локально на исходном тесте `200 / 6000 / 3000`, после перезапуска JVM.

| Показатель | Контроль прежнего кода | Итоговый код |
|---|---:|---:|
| Время до последнего результата | 130,3 с | **72,7 с** |
| SUCCESS | 5902 | **5931** |
| FAIL / ERROR | 6 / 0 | **0 / 0** |
| Результат не получен | 92 | 69 |
| SUCCESS от 6000 запрошенных тестов | 98,37% | **98,85%** |
| Расходы | 6,9505% | **6,8820%** |

Итоговый прогон стал примерно на **44% короче**. Во всех 14 непустых отсчётах минутная успешность составила 100%. Расходы — ровно 5931 × 30: лишних платных вызовов нет. В конце буфер и пул свободны. 69 тестов без итогового результата не считаю успешными.

Для сравнения проверил 220 мест без входного окна: получилось 67 секунд, но 345 FAIL и успешность ниже 97%. Этот вариант отклонён. В другом промежуточном прогоне расходы составили 7,0051% при нуле лишних платных вызовов: небольшой финансовый запас по-прежнему зависит от случайных сумм заказов. Все результаты, включая неудачные, сохранены в [optimization-result.json](optimization-result.json).

Новый удалённый прогон запускается только после публикации итоговой версии. Скриншот ниже относится к прежнему прогону 22 октября.

У 15 тестов нет итогового результата в счётчиках и логе, поэтому я не записываю их в успешные. Даже консервативные 99,75% выше требуемых 97%. Генератор замедлялся по 429, поэтому весь прогон занял больше исходных 30 секунд подачи нагрузки.

Финансовый запас маленький, но лишних платных вызовов нет: **5985 × 30 = 179 550**. Увеличением очереди или изменением скорости этот запас не поднять при тех же заказах и тарифе. Порог 93/7 выполнен по точным счётчикам этого прогона; следующий случайный набор заказов может дать другую долю.

Точные значения сохранены в [local-result.json](local-result.json). Графики используют `increase()` и дают оценку, которая может отличаться от разности исходных счётчиков.
