# Кейс 4: буферизация и back pressure

Аккаунт `acc-18`, нагрузка 200 покупок/с, 6000 покупок, бюджет оплаты 3000 мс.
Лимиты аккаунта: 110 запросов/с, до 10000 параллельных вызовов, средняя
обработка 1 с, стоимость вызова 30.

## Запуск

```properties
payment.backpressure.enabled=${PAYMENT_BACKPRESSURE_ENABLED:true}
payment.processing-time-millis=${PAYMENT_PROCESSING_TIME_MILLIS:3000}
payment.processing-upper-bound-millis=${PAYMENT_PROCESSING_UPPER_BOUND_MILLIS:2000}
server.http2.enabled=${SERVER_HTTP2_ENABLED:false}
server.jetty.accept-queue-size=${SERVER_ACCEPT_QUEUE_SIZE:1024}
```

Бюджет магазина нужно согласовать с `processingTimeMillis` в тесте. После
изменения настроек требуется перезапуск. Исходные параметры нагрузочного
теста и дедлайны запросов не увеличиваются.

Верхняя граница 2000 мс — характеристика именно этого аккаунта, подтверждённая
кодом локального тестера: `acc-18` выбирает время обработки от 0 до 2000 мс.
В первом прогоне измерено среднее 986 мс, p95 1895 мс и максимум 1999 мс.
API аккаунта отдаёт только среднее, поэтому верхняя граница задаётся отдельно;
из одного среднего времени её нельзя вывести для произвольного аккаунта.

## Решение

Диспетчер заполняет свободные места HTTP-пула пачкой. Непосредственно перед
сетевой отправкой скользящее окно допускает не более 110 стартов за последнюю
секунду. Для проверки окна используется монотонное время. Блокирующее ожидание
учитывает дедлайн запроса, не создаёт фоновых потоков и не удерживает блокировку
на всё время ожидания.

Обязательного интервала между каждой парой отправок больше нет. В отдельном
эксперименте на Windows прежний интервал 9,09 мс фактически давал 15,39 мс,
то есть около 65 запусков/с вместо 110.

В `PaymentFlowLimits` рассчитываются:

```text
R = rateLimitPerSec
P = parallelRequests
T = averageProcessingTime, секунды
Tmax = payment.processing-upper-bound-millis / 1000
D = payment.processing-time-millis / 1000
Window = 1 с

μ = min(R, P / T)
C = ceil(μ × T)
W = max(0, D − Tmax − Window)
Q = floor(μ × W)
B = C + Q
RetryDelay = Window
```

Для кейса 4 получаются C = 110, Q = 0, B = 110 и пауза 1000 мс.
Секундный запас нужен на ожидание разрешения сетевого окна. Дополнительная
очередь не помещается в бюджет: приём ограничен 110 незавершёнными оплатами.
Этот лимит учитывает подготовку, внутренние очереди, ожидание окна и внешний вызов.
Место освобождается после завершения обработки, в том числе при ошибке.

Чтобы холодная JVM не получала сразу всю пачку из 110 оплат, входной лимит
начинается с одного места. После каждого завершения обработки он увеличивается
на одно до расчётного B. Это прогревает путь обработки реальными запросами;
фиктивные платежи при запуске не создаются. `payment_buffer_limit` показывает
текущий растущий лимит, `payment_buffer_capacity` — его расчётный максимум.

Если буфер заполнен, магазин немедленно возвращает HTTP 429 до изменения
заказа и создания события платежа. По контракту курса `Retry-After` содержит
абсолютный timestamp в миллисекундах. Тестер умеет замедлять и повторять нагрузку.
Пауза в одно окно позволяет не создавать шквал повторов каждые 10 мс.

При `payment.backpressure.enabled=false` входной лимит и связанные с ним 429
отключены. В `OrderPayer` возвращается очередь 8000 с ожиданием при переполнении;
ограничения внешней системы продолжают действовать.

В локальных прогонах с h2c тестер получал `RST_STREAM: Protocol error`.
Для проверяемой конфигурации магазин использует HTTP/1.1; HTTP/2 можно вернуть
флагом `SERVER_HTTP2_ENABLED=true`, но этот вариант требует отдельной проверки.
Очередь принятия TCP-соединений Jetty явно установлена в 1024: при системном
значении по умолчанию стартовые пачки сопровождались `ConnectException`.
Это очередь установления соединений, отдельная от платёжного буфера.

При нескольких настроенных аккаунтах существующая логика отправляет платёж
каждому из них. Входной лимит выбирается по минимальному B, а сетевые окна
и HTTP-пулы у аккаунтов отдельные. Решение проверяется для одного `acc-18`.

## Проверка

```powershell
.\gradlew.bat --offline test --tests ru.quipy.payments.logic.PaymentFlowLimitsTest --tests ru.quipy.payments.logic.PaymentBackPressureTest --tests ru.quipy.custom.PaymentCompletionTest --tests ru.quipy.custom.SlidingWindowRateLimiterTest bootJar --console=plain
```

Проверяются формулы, заполнение и освобождение буфера, оба режима флага,
HTTP 429 без изменения заказа, истечение дедлайна и скользящее окно при
конкурентных вызовах. Нагрузочный тест запускается запросом кейса 4
из `test-local-run.http` на локальном тестере.

Критерии курса: более 97% успешных тестов на протяжении прогона и соотношение
доходов/расходов не хуже 93/7. Для кейса 4 отдельно допускается результат ниже 100%.
Итоги нужно проверять по разности исходных счётчиков и логу одного прогона,
а не по округлённым `increase()` на графике с несколькими запусками.

## Подтверждённый локальный результат

22 октября 2026 года я запустил исходный запрос из `test-local-run.http`
сразу после перезапуска JVM, без предварительных фиктивных платежей.
Начало — 20:08:15, последний результат — 20:10:28 по Москве.

| Показатель | Результат |
|---|---:|
| `ratePerSecond` / `testCount` / `processingTimeMillis` | 200 / 6000 / 3000 |
| Подтверждённые SUCCESS | 5985 |
| FAIL / ERROR | 0 / 0 |
| Успешность среди учтённых тестером результатов | 100% |
| SUCCESS относительно всех 6000 запрошенных тестов | 99,75% |
| Минутная успешность Prometheus, 27 непустых отсчётов | 100% во всех отсчётах |
| Доход | 2 406 603 |
| Расходы | 179 550 |
| Доходы / расходы | 93,0573% / 6,9427% |

Тестер завершил запуск на `testNum = 6000`, но для 15 тестов в итоговых
счётчиках и логе нет результата. Я не считаю их успешными: даже при таком
консервативном подсчёте получается 99,75%, выше порога 97%.
В логе подтверждены 5985 успешных оплат; ошибок соединения и предупреждений
о паузах JVM в этом прогоне не было. Прогон дольше исходных 30 секунд подачи
нагрузки, поскольку генератор замедляется по HTTP 429.

Критерии курса выполнены. Снимок точных счётчиков и расчётов сохранён
в [local-result.json](local-result.json). 24 целевых автоматических теста прошли.

Диагностика текущей проверки находится в игнорируемом каталоге
`build/case4-validation/`: лог приложения, замаскированный лог тестера и метрики.

Полезные метрики: `payment_buffer_size`, `payment_buffer_capacity`,
`payment_admission_rejected_total`, `payment_queue_size`, `payment_active`
и `payment_queue_wait_seconds`. Gauge отображаются напрямую;
для счётчика отказов используется `rate(payment_admission_rejected_total[30s])`.
